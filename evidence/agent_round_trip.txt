# The agent-facing capability interface, end to end (stretch goal S1)

`uv run python scripts/watch_agent_call.py`, transcript as printed.

`cua catalog --json` is shelled out for real; its output is sent as `tools` on a
Messages API call to claude-sonnet-5; the model's `tool_use` blocks are resolved
back to their artifact and dispatched to the M3 replay engine; the results come
back as `tool_result` blocks the model answers from. Nothing here is staged.

R-M7-1 is visible at the top: on the committed directory both capabilities are
drafts, so the catalog offers nothing. The script approves the read-only one in a
copy, which is why the repo's own `cua catalog` still lists nothing.

This run uses `member.lookup_balance@1.1.0`. The earlier 1.0.0 shipped the
discovery goal as its description, and on every run the model read "Search for
member 99999, which does not exist..." and spent a whole replay on it before
answering the question asked -- two tool calls where one was needed. R-M7-2 fixed
that: the description below is human-authored, the goal is kept in
`provenance.discovery_goal`, and `cua approve` now refuses a capability described
by its own goal. One call, straight to the answer.

`member_name` still reaches the model as `<redacted>` while the engine read
"Dana Whitfield". A tool result is a prompt on the caller's next turn, so it is
rendered from `evidence_outputs`. The cost is real and stated in REPORT.md
section 7: a capability whose purpose was reading a name could not be answered
this way.

THE SAME INTERFACE, WITH AN ARGUMENT THE ARTIFACT REFUSES
`uv run python scripts/watch_agent_call.py --bad-argument`

Defence in depth, and the layers are independent. The model declines first --
the `^\\d{5}$` is in the schema it was handed, so it never makes the call. The
dispatch path is then given the call it would have had to make, and refuses it
in milliseconds with no browser navigation, as a tool result the model could act
on.

step 2 — the model chooses  (claude-sonnet-5, one call)
──────────────────────────────────────────────────────────────────────────────
  user  What's the savings balance for member ABC-123? That is the id exactly as the member gave it; pass it through unchanged.

  reasoning   I can't use "ABC-123" as-is — the member ID field requires exactly 5 digits (e.g., 00123), and "ABC-123" contains letters and a hyphen, so it doesn't fit that format.

Could you double check the ID with the member? A few possibilities:
- They may have given a different type of identifier (e.g., account number or username) rather than the 5-digit member ID.
- If "123" is the actual numeric part, the correct ID might be something like 00123 — but I don't want to guess incorrectly.

Please confirm or provide the correct 5-digit member ID, and I'll look up the savings balance right away.

  The model declined -- the pattern is in the schema it was handed, so it
  never made the call. Defence in depth: the artifact refuses it too. Forging
  the call to prove the dispatch path does not depend on the model's judgement.
